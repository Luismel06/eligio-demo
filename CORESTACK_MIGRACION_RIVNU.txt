CORESTACK / RIVNU
GUIA OPERATIVA PARA CODEX EN VM2

Fecha de preparacion: 2026-08-10
Estado: plan de migracion. No ejecutar un corte a produccion sin completar
las validaciones y los puntos de aprobacion indicados aqui.

===============================================================================
1. OBJETIVO
===============================================================================

Migrar la aplicacion RIVNU desde la infraestructura temporal:

  Vercel Web + Vercel API + PostgreSQL/Supabase

hacia infraestructura privada CoreStack, manteniendo la aplicacion, la base de
datos, los usuarios, roles, tenant y configuracion de empresa.

CoreStack es una plataforma multi-tenant. RIVNU es uno de sus tenants, no una
aplicacion aislada ni una excepcion arquitectonica. Esta migracion prepara el
workload inicial de RIVNU, pero debe preservar la capacidad de CoreStack de
servir futuras empresas desde el mismo producto:

  - las reglas de negocio siguen siendo tenant-aware;
  - las tablas operativas siguen aisladas por tenantId y por guards de la API;
  - no se crean forks de codigo, schemas por cliente ni atajos de acceso directo
    a la base para RIVNU;
  - cualquier configuracion exclusiva de RIVNU debe quedar externalizada como
    configuracion/despliegue, no incrustada en logica compartida.

El resultado objetivo es:

  Internet
    -> VM1 Gateway (Nginx + TLS)
    -> VM2 App (Next.js Web + NestJS API)
    -> VM3 SQL DB (PostgreSQL privado)

VM4 Billing Gateway queda reservado para una futura integracion de pagos/AZUL y
DGII. No debe recibir trafico ni codigo operativo de RIVNU durante esta
migracion.

La empresa/plataforma se llama CoreStack. Algunos nombres tecnicos historicos,
por ejemplo paquetes @qorvex, pueden seguir existiendo en el codigo. NO deben
renombrarse como parte de esta migracion: seria una tarea separada y riesgosa.

2. TOPOLOGIA Y RUTAS
===============================================================================

VM1 - Gateway
  IP privada: 10.0.0.2
  Responsabilidad: unico punto de entrada publico, Nginx, TLS, redireccion
  HTTP -> HTTPS, proxy inverso, limites de carga y cabeceras de seguridad.

VM2 - App
  IP privada: 10.0.0.3
  Responsabilidad: repositorio, build reproducible, contenedores/procesos de:
    - Web Next.js (solo accesible desde VM1)
    - API NestJS (solo accesible desde VM1 y VM3 si hiciera falta)
  Ruta prevista:
    /opt/corestack/apps/rivnu/repo
  Datos persistentes locales previstos:
    /opt/corestack/apps/rivnu/data

Red Docker existente en VM2:
  rivnu-network
  Driver: bridge
  Scope: local

Esta red es la red de workload/despliegue de RIVNU, NO el mecanismo de
aislamiento del tenant. El aislamiento multi-tenant real permanece en la API,
los guards, los permisos y PostgreSQL. No crear redes Docker distintas como
sustituto de tenantId.

Diseno Docker objetivo para RIVNU (todavia no desplegar):

  rivnu-network
    ├── rivnu-web  (Next.js, escucha 3000 dentro del contenedor)
    └── rivnu-api  (NestJS, escucha 4000 dentro del contenedor)

Cada contenedor tendra un solo puerto publicado en la IP privada de VM2, solo
para que VM1 pueda hacer proxy:

  rivnu-web: 10.0.0.3:3001 -> contenedor:3000
  rivnu-api: 10.0.0.3:4001 -> contenedor:4000

Los puertos 3000 y 4000 no deben exponerse a Internet. VM1 sera quien reciba
80/443 y haga proxy a esos dos puertos privados. La regla de firewall exacta se
definira luego del inventario: solo VM1 debe poder alcanzar 3001/4001 en VM2.

Referencia historica recibida:

  image: qorvex/rivnu:latest
  container_name: qorvex-rivnu
  ports: 3001:3000

Ese era un modelo de un solo contenedor y nombre historico. No reutilizarlo ni
reemplazar contenedores existentes a ciegas. El objetivo nuevo es separar Web y
API en rivnu-web y rivnu-api dentro de rivnu-network.

VM3 - SQL DB
  IP privada: 10.0.0.4
  Responsabilidad: PostgreSQL exclusivo de produccion RIVNU/CoreStack.
  PostgreSQL no debe quedar accesible desde Internet; solo VM2 y administracion
  controlada por SSH/VPN/red privada.

VM4 - Billing Gateway
  IP privada: 10.0.0.1
  Responsabilidad futura: integracion aislada de AZUL/Verifone/DGII.
  Estado para esta fase: inventariar y dejar aislada; NO desplegar RIVNU aqui.

Estructura CoreStack ya creada en VM2:
  /opt/corestack/apps/rivnu/repo
  /opt/corestack/apps/rivnu/data

3. APLICACION QUE SE MIGRA
===============================================================================

Repositorio: monorepo pnpm CoreStack.

  apps/web             Next.js 15, interfaz web.
  apps/api             NestJS 11, API REST y reglas de negocio.
  packages/database    Prisma 6, esquema y migraciones PostgreSQL.

Comandos relevantes desde la raiz del repositorio:

  corepack pnpm install --frozen-lockfile
  corepack pnpm db:generate
  corepack pnpm --filter @qorvex/database build
  corepack pnpm --filter @qorvex/api build
  corepack pnpm --filter @qorvex/web build
  corepack pnpm lint
  corepack pnpm db:migrate:deploy

Requisitos de runtime:

  - Node.js 22 LTS.
  - Corepack.
  - pnpm 10.12.4 (esta fijado en package.json).
  - PostgreSQL 17 recomendado en VM3, o una version compatible validada.
  - Docker Engine + Docker Compose plugin en VM2 si se elige Compose.

El docker-compose.yml actual del repositorio es SOLO para PostgreSQL local de
desarrollo y publica 5432. No usarlo ni adaptarlo a ciegas para produccion. El
repositorio aun no tiene Dockerfiles, Compose productivo, unidades systemd ni
configuracion Nginx de produccion: deben diseniarse como artefactos nuevos,
revisables y separados del compose de desarrollo.

La arquitectura es un monolito modular: no convertirla en microservicios ni
separar Web/API/DB en proyectos de codigo distintos durante la migracion.

Antes de modificar infraestructura, Codex debe analizar TODO el repositorio y
entregar un mapa de arquitectura que distinga claramente:

  - componentes globales CoreStack;
  - limites de tenant y uso de tenantId;
  - modulos RIVNU configurables versus logica compartida;
  - Web, API, Prisma/migraciones y dependencias externas;
  - configuracion Vercel/Supabase heredada que se reemplazara;
  - puntos donde una futura empresa podria agregarse sin copiar codigo.

Autenticacion y datos:

  - La autenticacion es propia: JWT + bcrypt + NestJS + Prisma.
  - NO se usa Supabase Auth, Supabase REST, Realtime ni Edge Functions.
  - El frontend siempre debe hablar con la API NestJS; nunca directamente con
    PostgreSQL.
  - OCR de facturas se ejecuta en el navegador. La captura movil QR no guarda
    fotografias; devuelve temporalmente datos OCR estructurados.
  - La integracion fiscal/pagos actual es MOCK; VM4 queda para el futuro.

Almacenamiento de imagenes:

  - La aplicacion puede usar Supabase Storage para imagenes de productos.
  - Los objetos de Storage NO viajan en un pg_dump.
  - No bloquear la primera migracion por Storage si no hay catalogo productivo
    cargado todavia. Mantener Supabase Storage temporalmente o preparar un
    almacenamiento privado persistente posteriormente; no cambiar URLs de
    imagenes sin un plan de migracion de objetos.
  - Si se opta por almacenamiento local, no guardar archivos dentro de una
    imagen efimera: montar un volumen persistente y servirlo de forma segura.

===============================================================================

  - Branding.

CoreStack. Toda consulta, dump de validacion y operacion de datos debe declarar

NUNCA ejecutar en la base objetivo de produccion:

  - pnpm db:seed

  - db:cleanup:rivnu

5. PRINCIPIOS OBLIGATORIOS DE SEGURIDAD
===============================================================================

1. No guardar, mostrar, registrar ni poner en Git contrasenas, tokens,
   DATABASE_URL completas, JWT_SECRET, llaves SSH ni contenido de archivos .env.

2. Si una clave o contrasena fue compartida en una conversacion, considerarla
   expuesta y pedir que sea rotada. No reutilizarla en scripts.

3. Usar llaves SSH ed25519, no contrasena, entre VM2 y las demas VMs.
   Configurar aliases concretos en ~/.ssh/config y validar fingerprints.

4. Emplear cuentas de minimo privilegio:
   - usuario administrativo para preparacion controlada;
   - usuario runtime de aplicacion separado;
   - usuario migrador de PostgreSQL separado del usuario runtime.

5. No exponer directamente al Internet:
   - PostgreSQL (5432),
   - Next.js (3000),
   - NestJS (4000),
   - Docker daemon,
   - puertos de desarrollo,
   - transportes internos de Codex.

6. VM1 sera el unico host con 80/443 publicos. VM2 y VM3 deben aceptar solo
   trafico privado necesario. Verificar UFW/iptables/nftables y no aplicar una
   regla sin saber primero el estado actual.

   Si se habilita TRUST_PROXY=1 en la API, Nginx de VM1 debe establecer y
   sobrescribir X-Forwarded-For, X-Real-IP y X-Forwarded-Proto correctamente.
   La aplicacion puede usar allowlists de IP internas; no permitir que clientes
   externos falsifiquen estas cabeceras llegando directo a VM2.

7. Antes de cualquier accion destructiva, mostrar el plan, el alcance, el
   backup disponible y pedir aprobacion explicita.

8. No hacer git reset --hard, git clean, checkout destructivo, migraciones
   reset, borrados recursivos ni restauraciones sobre una base no vacia sin una
   aprobacion explicita y una ruta de rollback.

10. VARIABLES DE ENTORNO DE PRODUCCION
===============================================================================

Crear un mecanismo seguro para variables (por ejemplo archivos .env con
permisos 600 fuera del repositorio, secrets de Docker o gestor de secretos).
No crear secretos ficticios para produccion ni versionarlos.

Variables API esperadas, con valores reales proporcionados fuera de Git:

  DATABASE_URL
  DIRECT_URL
  JWT_SECRET                <- conservar el secreto actual si se desea mantener
                               sesiones existentes; durante un corte limpio se
                               puede rotar con plan de relogin.
  JWT_EXPIRES_IN
  CORS_ORIGIN               <- dominio HTTPS exacto del Web, sin '*'.
  NODE_ENV=production
  TRUST_PROXY=1             <- solo tras confirmar el proxy de VM1.

Variables Web esperadas al construir:

  NEXT_PUBLIC_API_URL       <- URL HTTPS final de la API.
  NEXT_PUBLIC_APP_URL       <- URL HTTPS final del Web; necesaria para QR OCR.
  NODE_ENV=production

Importante: las variables NEXT_PUBLIC_* quedan incorporadas al build de Next.js.
Definir dominios finales antes del build de produccion y reconstruir si cambian.

No incluir variables NEXT_PUBLIC_SUPABASE_* en Web. La aplicacion no usa
Supabase Auth ni acceso directo a tablas.

En produccion, usar un JWT_SECRET fuerte (minimo 32 caracteres, no conocido ni
vacio) y un CORS_ORIGIN HTTPS explicito. Si se preserva el JWT actual, validar
primero que cumple estas condiciones; si se rota, incluir el relogin dentro del
plan de corte.


===============================================================================
11. FASE 3 - MIGRACION DE POSTGRESQL (ENSAYO PRIMERO)
===============================================================================

La migracion debe realizarse primero como ensayo completo a una base aislada en
VM3. Nunca aplicar migraciones Prisma antes de restaurar un dump completo del
schema origen: el dump ya incluye schema, datos, funciones, triggers y tabla
_prisma_migrations.

Procedimiento de ensayo:

  1. Instalar/usar cliente pg_dump compatible con la version del PostgreSQL
     origen. Confirmar versiones antes de empezar.
  2. Crear backup completo de la base origen en formato custom, sin propietarios
     ni privilegios:

       pg_dump --schema=public --format=custom --no-owner --no-privileges ...

     La URL/credencial debe llegar por un archivo protegido o prompt seguro,
     nunca aparecer en logs, comandos persistidos ni Git.

  3. Calcular SHA-256, guardar fecha, tamano y salida de pg_restore --list.
  4. Restaurar en una database temporal/vacia de VM3.
  5. Comparar:
       - prisma migrate status;
       - numero de tablas y migraciones;
       - conteos por tablas clave;
       - tenant RIVNU, usuarios/membresias, branding, caja y secuencias;
       - login y endpoints de solo lectura contra la API de ensayo.
  6. Ejecutar db:migrate:deploy SOLO si existen migraciones posteriores al dump.
  7. Documentar duracion, errores, comandos y rollback.

No se debe usar seed para poblar la base de produccion.

Datos/Storage:

  - pg_dump no migra objetos de Supabase Storage.
  - Inventariar objectos y URLs antes de decidir MinIO/S3/almacenamiento privado.
  - No eliminar buckets ni imagenes origen durante el ensayo.

13. FASE 5 - CORTE A PRODUCCION
===============================================================================

Solo iniciar cuando ensayo, backups, dominios, TLS, monitoreo y rollback hayan
sido aprobados.

Secuencia de corte:

  1. Anunciar ventana de mantenimiento y congelar escrituras en Vercel/API
     origen. Evitar que caja, ventas o importaciones generen diferencias.
  2. Hacer backup final del origen, verificar hash y catalogo de restore.
  3. Restaurar ese backup final en la database final vacia de VM3.
  4. Validar migraciones y conteos contra el origen.
  5. Aplicar solamente migraciones posteriores si corresponde.
  6. Desplegar el commit/tag ya validado en VM2 con variables finales.
